1. Изменяются **только строковые значения**. Добавление/удаление/перестановка элементов массивов — запрещены (§4).

5. Хардкод-узлы (§12) не переносятся в JSON — соответствующих полей не существует, и админка не должна их предлагать.

## 4. Проблема позиционных индексов

**Суть:** шаблон обращается к данным по литеральным индексам — `{S['modal-core'].blocks[2].heading}`, `{S['modal-sites'].cards[4].desc}` и т. д. Данные и шаблон связаны позиционно: вставка/удаление/перестановка элемента массива ломает рендер (несуществующий индекс → `undefined` в HTML или падение сборки).

**Варианты:**

1. **Заморозка структуры (рекомендация для Этапа 2).**
   - UI: у блоков/карточек/пунктов — только редактирование значений, кнопок add/remove/reorder нет;
   - Schema: `minItems = maxItems` по таблице §3.1;
   - Инструмент `tools/admin/check-bindings.mjs`: парсит все `{S[…].a[0].b}` и `{L.*}/{M.*}/{site.*}` из `SpatialWorkbench.astro` и `index.astro` и проверяет: (а) каждый индекс/ключ существует в JSON → иначе **ошибка**; (б) элемент массива не упомянут в шаблоне → **warning** (мёртвые данные); (в) поле отсутствует и это один из 8 хардкод-узлов → **норма** (белый список).
   - Цена: нельзя добавить новый блок без правки шаблона (это и правильно — новый блок = новая вёрстка).
2. **Рефакторинг на циклы** (`blocks.map((b,i)=>…)` в шаблоне) — снимает проблему полностью, но меняет вывод whitespace → **новый baseline + полная перепроверка идентичности**. Отдельный Этап 3, отдельное решение.
3. **Стабильные id + `find()`** — тоже правка шаблона, аналогичные издержки.

**Этап 2 = вариант 1.** Админка принципиально не меняет структуру — только значения строк.

## 5. Валидация

Уровни (в порядке выполнения при сохранении):

1. **JSON Schema** — типы, обязательные ключи, точные длины, `additionalProperties: false`.
2. **Binding-checker** — связь «шаблон ↔ JSON» (§4).
3. **Бизнес-правила:**
   - Ссылки (`links.json`, `actions`, `screenBadge`, любые URL-поля):
     `^(https://[A-Za-z0-9.-]+(:[0-9]+)?(/[^\s]*)?|mailto:[^\s@]+@[^\s@]+#[A-Za-z0-9_-]+|#[A-Za-z0-9_-]+|/[^\s]*)$`
     Запрещены: `javascript:`, `data:`, `vbscript:`, протокол-относительные `//…`, логины/пароли в URL. Заглушки `#youtube`/`#instagram` — допустимы.
   - `media`: путь из белого списка `/previews/…`, файл существует в `public/`, размер ≤ 2 МБ, расширение jpg/png/webp/svg.
   - Длины (warning, не блокер): title ≤ 70, description ≤ 160, текст блока ≤ 500 символов.
   - Спецсимволы `& < > ' "` — **разрешены** (Astro экранирует, вывод корректен). UI показывает предпросмотр «как будет в HTML» (экранированный). XSS-строка `<img src=x onerror=alert(1)>` обязана отображаться как текст.
   - Trailing/leading пробелы и «пустые обязательные строки» → ошибка или warning с показом дифа; **никаких автоматических правок молча**.
4. После валидации — сериализация и сравнение с исходником: если данные не менялись, файл должен быть побайтово идентичен (регресс against round-trip).

## 6. Безопасная запись JSON

Алгоритм `POST /api/save`:

1. Тело ≤ 1 МБ, `Content-Type: application/json`, токен проверен.
2. Валидация (§5) → при ошибке `422` с перечнем полей, **файлы не тронуты**.
3. Проверка `If-Match: <etag>` → `409`, если файл уже изменился (§7).
4. Лок `src/data/.admin.lock` (§7).
5. Бэкап текущего файла (§10).
6. Атомарная запись **одного файла**:
   - `src/data/.tmp/<имя>.<pid>.<rand>.tmp` — временный файл **в той же файловой системе** (обязательное условие атомарности `rename`);
   - `writeFileSync` → `fsyncSync(fd)` → `close` → `renameSync(tmp, target)` (на POSIX атомарно);
   - один HTTP-запрос = один файл → состояние либо старое, либо новое, «наполовину» не бывает;
   - кросс-файловые правки → последовательные запросы (обычно правится один файл за раз);
   - при любом сбое — `unlink(tmp)`, цель не тронута.
7. Новый ETag в ответе, запись в audit-log, снятие лока.

Формат: `JSON.stringify(obj, null, 2) + '\n'` (кириллица не экранируется, порядок ключей сохраняется — `JSON.parse` сохраняет порядок вставки). Подтверждается round-trip тестом.

## 7. Защита от одновременной записи

1. **Один экземпляр сервера:** слушает фиксированный порт (4310) → второй экземпляр получает `EADDRINUSE` и не стартует.
2. **Lock-файл** `src/data/.admin.lock`: создаётся через `wx` (O_EXCL), содержит `{pid, startedAt, token-hash}`. Занят → `409 Conflict`. Протухший (старше 30 с или pid не существует) → перехват с записью в лог.
3. **Оптимистическая блокировка:** клиент шлёт `If-Match: <sha256 загруженного файла>`; сервер сравнививает с текущим состоянием диска → расхождение → `409 «файл изменён вне админки, перезагрузите»`. Не даёт потерять чужую правку, даже если лок снят.
4. Нет второго канала записи: API не имеет параметра «имя файла» — фиксированный список из 4 имён (исключает path traversal).

## 8. Доступ к /admin

Вариант A (локальная):

- Слушает **только `127.0.0.1`** (не `0.0.0.0`).
- Токен: `crypto.randomBytes(32).toString('hex')` при первом запуске → `tools/admin/.token` (права `0600`, в `.gitignore`) либо `ADMIN_TOKEN` в `.env.local` (уже игнорируется git).
- Все `/api/*` требуют `Authorization: Bearer <token>` → иначе `401` без деталей.
- UI: поле ввода токена → `sessionStorage` (не localStorage, не URL, не логи).
- Rate limit: 5 неудачных попыток за минуту → `429` + пауза.
- Проверка `Origin`/`Host` (только localhost), CORS не открывать.
- `audit.log` (gitignored): время, действие, файл, sha256 до/после.

Вариант B (будущее, если понадобится): nginx `location /admin` → `auth_basic` (htpasswd) → `proxy_pass http://127.0.0.1:4310`; порт приложения наружу не торчит; дополнительно fail2ban/rate-limit.

## 9. Как не допустить публикации незащищённой админки в dist

1. **Физическое отсутствие:** UI и сервер лежат в `tools/admin/` — вне `src/`, Astro их не собирает. В `dist` их нет by design.
2. **Запрет в правилах проекта:** не добавлять `src/pages/admin.astro` (если когда-либо — только с auth и dev-guard, но рекомендация: не добавлять никогда).
3. **Автопроверка `npm run verify:dist`** (скрипт `tools/admin/verify-dist.mjs`):
   - список файлов `dist/` не содержит `admin`, `api`, `tools`, `.token`;
   - grep содержимого `dist/**` на маркеры админки (строку `admin-ui`, `/api/save`);
   - `dist` содержит ровно ожидаемый набор (сверка с манифестом baseline — те же 56 файлов, пока вёрстка не менялась).
   - Скрипт добавляется в шаг деплоя **перед** `rsync` (правка DEPLOY.md — отдельное подтверждение).
4. **Деплой копирует только `dist/`** → на VPS файлы админки не попадают физически (вариант A).
5. `.gitignore` дополняется: `tools/admin/.token`, `tools/admin/audit.log`, `src/data/.backups/`, `src/data/.admin.lock`, `src/data/.tmp/`.

## 10. Резервное копирование и откат

1. **Автобэкап:** перед каждой записью копия целевого файла → `src/data/.backups/<имя>.<UTC-ISO>.json` (двоеточия времени заменяются на `-`). Хранить: последние 100 файлов и не старше 30 дней (чистка при каждом сохранении).
2. **UI «История»:** список бэкапов с дифом к текущему состоянию; «Восстановить» → та же цепочка (бэкап текущего → валидация → атомарная запись).
3. **Git как основной откат** (рекомендация): после каждой осмысленной правки — `git add src/data && git commit -m "content: …"`. Откат: `git checkout -- src/data`. Авто-коммит при сохранении — решение пользователя (§14.3), по умолчанию **выключен**.
4. **Перед деплоем:** `npm run build` → сверка с baseline → только ожидаемые дифы → rsync. Откат деплоя: `rsync` предыдущей сборки или `git revert` + rebuild.

| # | Тест | Критерий |

| 10 | Интеграционный цикл | правка одного текста → build → diff к baseline **только** в ожидаемых строках; откат → build → `dist == baseline` (sha256 `9cafc09f…`) |

## 14. ⚠️ Архитектурные решения, требующие ТВОЕГО подтверждения

1. **Вариант админки:** A — локальная dev-only (рекомендую) / B — на VPS с basic auth / C — через CI.
2. **Правка `package.json`** (новые скрипты `admin`, `verify:dist`) и дописывание `.gitignore` — разрешаешь? (без этого план исполним частично)
3. **Авто-коммит git при сохранении:** нет (рекомендую) / да (коммит на каждую правку).
4. **Позиционные индексы:** заморозка структуры в Этапе 2 (рекомендую) / или сразу рефакторинг шаблона на циклы (Этап 3, требует нового baseline и повторного доказательства идентичности).
5. **Место схем:** `tools/admin/schema/` (рекомендую — `src/data` остаётся чисто контентом) / `src/data/schema/`.
6. **Аутентификация (вариант A):** случайный токен в файле (рекомендую) / пользовательский пароль.
7. **Кнопка «Собрать и сравнить с baseline» прямо в админке** (запуск `npm run build` + diff) — включать в Этап 2 или сборка остаётся ручной командой?
8. **Инструменты в репозитории:** `check-bindings.mjs`, `verify-dist.mjs` — положить в репо (рекомендую); одноназовый извлекатель `extract_content.py` — вернуть в репо как инструмент контроля или оставить вне репозитория?
